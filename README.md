# Software Factory

GitHub-native orchestration extracted from Dev Agent Harness v0.1 (source commit
`615fbee4775c3eea46270531d8a13648d998d835`). SF owns planning, project autonomy,
approval, Issue/PR lifecycle, dependencies, priority, persistent journals, worker
selection/dispatch/supervision, global concurrency, retries and reporting.

[Dev Agent Harness](https://github.com/munichdeveloper/dev-agent-harness) executes
one supplied run through contract 2.0. SF validates authorization before invoking
its standalone CLI, strips credentials from its subprocess environment, validates
the result and persists it. SF never implements the digest worker itself.

## Install

Run `npm ci --ignore-scripts`, then
`npx tsx scripts/install.ts --directory TARGET --ref FULL_FACTORY_COMMIT_SHA`.
This preserves existing files and installs `.github/software-factory.yml` and
`.github/workflows/factory-manager.yml`. Merge into the target default branch.
The bundled composite Action is pinned by the wrapper; `runtime.json` records
the independently pinned public Harness. No checkout of private SF code with a
target token is needed. The checked-in bundle is reproducibly generated by CI.

This repository is private: GitHub Actions access must allow the owner's other
private repositories. Public targets cannot consume this private action. No
visibility change is made; use a public distribution if that becomes necessary.

Dispatch bootstrap once to create missing labels, then manager. Defaults are
supervised and mock planning. To enable OpenAI, set `llm.provider: openai` and
the target Actions secret `OPENAI_API_KEY`. All project-level settings, including
`factory.enabled`, `factory.scope`, autonomy overrides, worker limits and retries,
belong in the SF configuration. The Harness has no such configuration.

For persisted-state compatibility, SF retains existing `harness:*` GitHub labels,
follow-up keys and SF delegation envelope 1.0. New journals use
`software-factory:v1`; legacy `dev-agent-harness:v1` comments and old worker run
names are accepted. These are SF's storage compatibility, not Harness features.
See [migration](docs/migration.md) and [configuration](docs/configuration.md).

## Development

`npm run check`, `npm run test:coverage`, `npm run schemas`, `npm run bundle`.
Build the pinned Harness separately, set `HARNESS_ENTRYPOINT` to its absolute
`dist/cli.js` path, then run `npm run test:integration`. CI checks out that exact
runtime, runs the real cross-repository protocol test and rejects bundle/schema
drift. No production coding or review worker or automatic PR merging is included.
