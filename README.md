# Software Factory

Optional [Slack notifications](docs/slack.md) route individually enabled SF issue
creation and bot-performed SF PR merge events to configurable channels. Use a
`chat:write` bot connection through `SLACK_BOT_TOKEN`; default is disabled.

GitHub-native orchestration extracted from Dev Agent Harness v0.1 (source commit
`615fbee4775c3eea46270531d8a13648d998d835`). SF owns planning, project autonomy,
approval, Issue/PR lifecycle, dependencies, priority, persistent journals, worker
selection/dispatch/supervision, global concurrency, retries and reporting.

[Dev Agent Harness](https://github.com/munichdeveloper/dev-agent-harness) executes
one supplied test run through contract 2.0 or coding run through contract 3.0. SF validates authorization before invoking
its standalone CLI, strips credentials from its subprocess environment, validates
the result and persists it. SF never implements the digest worker itself.

## Install

Run `npm ci --ignore-scripts`, then
`npx tsx scripts/install.ts --directory TARGET --ref FULL_FACTORY_COMMIT_SHA`.
This preserves existing files and installs `.github/software-factory.yml` and
`.github/workflows/factory-manager.yml`. Merge into the target default branch.
The bundled composite Action is pinned by the wrapper; `runtime.json` records
the independently pinned public Harness. No checkout of private SF code with a
target token is needed. The checked-in bundle is reproducibly generated by CI.

This repository is public. Public and private targets can consume its pinned
Action when their Actions policy permits it. Version
[v0.1.0](https://github.com/munichdeveloper/software-factory/releases/tag/v0.1.0)
is pinned by `6c7eacdc1d93396f13ab33a1c187fa2c3565db43`. The initial release
source describes its pre-publication private distribution; this public release
needs no cross-repository PAT or private-action sharing setup.

Dispatch bootstrap once to create missing labels, then manager. Defaults are
supervised and mock planning. To enable OpenAI, set `llm.provider: openai` and
the target Actions secret `OPENAI_API_KEY`. All project-level settings, including
`factory.enabled`, `factory.scope`, autonomy overrides, worker limits and retries,
belong in the SF configuration. The Harness has no such configuration.

For persisted-state compatibility, SF retains existing `harness:*` GitHub labels,
follow-up keys and SF delegation envelope 1.0. New journals use
`software-factory:v1`; legacy `dev-agent-harness:v1` comments and old worker run
names are accepted. These are SF's storage compatibility, not Harness features.
See [migration](docs/migration.md) and [configuration](docs/configuration.md).

## Development

`npm run check`, `npm run test:coverage`, `npm run schemas`, `npm run bundle`.
Build the pinned Harness separately, set `HARNESS_ENTRYPOINT` to its absolute
`dist/cli.js` path, then run `npm run test:integration`. CI checks out that exact
runtime, runs the real cross-repository protocol test and rejects bundle/schema
drift. Optional [AI-reviewed PR merging](docs/merging.md) is disabled by default.
It requires a real code-review decision and native GitHub gates; green CI alone
does not authorize a merge. Existing PRs can be explicitly enrolled by label.
A [concept for per-PR preview environments](docs/preview-environments.md) on Coolify
(not implemented) describes an additional E2E gate before merging. A
[concept for risk-based auto-merge](docs/risk-based-merge.md) (not implemented) lets
the Factory merge low-risk PRs on its own and ask for approval above a threshold.

## Deployment after pushes (v0.5.0)

Optional [docker-ssh deployment](docs/deploy.md) ships the default branch to a
Docker host such as a Hostinger VPS: after the configured CI workflows succeeded
(or directly after the push), SF uploads the exact commit over SSH with a pinned
host key, runs `docker compose up --build --wait`, verifies health, switches the
release and rolls back on failure. Disabled by default; install the wrapper with
`--deploy` (optionally `--no-manager` for deployment only).

## Real Codex coding worker (v0.2.0)

Install with `npx tsx scripts/install.ts --directory TARGET --ref FULL_FACTORY_COMMIT_SHA --coding`.
Existing files are preserved: compare with `templates/factory-manager-coding.yml`
when upgrading. Set the target Actions secret `OPENAI_API_KEY` and enable Actions
to create pull requests in repository Settings → Actions → General.

```yaml
workers:
  test:
    enabled: false
  coding:
    enabled: true
    agent: codex
    model: gpt-6.1-sol
    reasoningEffort: high
  review: false
```

`llm.*` configures SF planning independently. `workers.coding.*` selects the actual
Codex agent and its model/effort. Coding takes precedence when both worker types
are enabled. The default installation remains supervised with the test worker.
The coding wrapper is required; the old single-job wrapper supports only test runs.
Optionally set `workers.coding.validationWorkflow: test.yml` to explicitly dispatch
product CI on the generated branch. That workflow must accept `workflow_dispatch`:
GitHub suppresses normal push/PR workflow triggers for writes made by `GITHUB_TOKEN`.

The reusable SF coding workflow has three jobs: reauthorize and freeze the base;
execute the pinned Harness with contents-read only; reauthorize again and publish
in a fresh job through GitHub's Git Data API. The worker receives neither a GitHub
write credential nor the raw OpenAI key. SF rejects unrelated, oversized, invalid,
symlink and control-plane changes, reuses a stable execution branch/PR, and journals
the terminal result. A moved default branch fails publication so a retry can use
a fresh base. Missing/failed coding output is durably recorded. Runtime success
with no changes is blocked rather than treated as implementation completion.

Maximum policy autonomy is `profile: autonomous` with `expand_scope: allow`
(all other supported actions already allow by default). Resource budgets still
apply; autonomy does not imply unlimited parallelism or API spending. Protected
configuration and automatic merging are not granted to the coding agent.
