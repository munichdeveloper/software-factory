# Temporal execution runtime – migration in progress

The existing Factory planner, permission policy, immutable delegation intents and Harness contracts remain the authority. `execution.engine: temporal` replaces worker dispatch and observation with the durable runtime; it never falls back to GitHub Actions if unavailable. Omitted `engine` retains the existing installation behavior. This is preview `0.7.0-temporal.0`, not a released or deployed replacement for v0.6.0.

The private broker owns repository-scoped GitHub credentials and PostgreSQL receipts. A separate PINNED worker owns a verified workflow bundle and pinned Harness entrypoint. Worker subprocesses receive no GitHub, planning or broker credentials. The deterministic executor uses the real pinned Harness. The coding executor uses a tightly bound reusable Actions workflow for disposable compute; Temporal and the broker retain dispatch, gate, recovery and publication authority. The pinned Harness keeps Codex under its existing unprivileged account/API-proxy boundary. Do not interpret a digest-worker or deterministic artifact fixture as a completed model run.

## Boundaries

- Admission freezes numeric repository identity, Factory/Harness commits, workflow hash, deployment/build/queue, specification/input, base commit, configuration and policy. The broker verifies the trusted Factory intent before starting the workflow.
- Workflow IDs derive from repository ID and execution ID. PostgreSQL advisory locks serialize claims; a lost Temporal start response is reconciled against the actual history input binding before accepting its run ID.
- Human gates persist in the broker. Signals only wake the workflow; they do not carry permission. The Manager session supplies the actor server-side, CSRF checks protect mutations, and the broker checks the actor's live repository permission and exact binding. Revocation, changed policy/specification/base and unsupported releases block execution/publication.
- Completed result receipts can be reused without new writes after a later task change. A publication with an ambiguous response is reconciled against trusted GitHub journal evidence. The PostgreSQL effect broker serializes blob/tree/commit/branch/Draft-PR/comment claims and receipts. Immutable Git objects may be retried by content; PRs/comments/dispatches without evidence remain blocked. This does not yet cover all existing Manager label/issue side effects from WF-06A.
- Existing PINNED runs accept only their original release or an explicitly retained release. Startup refuses a registry which would orphan an open recorded run. Human wait does not consume the ordinary worker timeout. No automatic migration of running workflows is implemented.

## Running an isolated development instance

Build with Node 22.12+ or Node 24 and `npm ci && npm run build`. Build the pinned Harness from `runtime.json` in `.runtime/harness`.

`npm run runtime:pack -- --factory-sha COMMIT --harness-sha COMMIT --harness ABSOLUTE_HARNESS_CLI --deployment NAME --build BUILD --queue QUEUE` writes a verified workflow bundle and worker package. Pack only a clean immutable source snapshot. Keep every package referenced by an open workflow.

The broker `npm run runtime:serve -- --file REGISTRY.json` reads `TEMPORAL_ADDRESS`, `FACTORY_RUNTIME_DATABASE_URL`, `FACTORY_MANAGER_TOKEN` and `FACTORY_WORKER_TOKEN`. Manager/worker tokens must be distinct and at least 32 characters. It binds loopback port 8095 by default. Use protected transport when exposing it beyond loopback; do not publish Temporal/PostgreSQL or grant workers Docker access.

Registry format: `{ "namespace": "software-factory-poc", "repositories": [{ "repositoryId": 123, "repository": "owner/repo", "githubTokenEnv": "SF_GH_TEST_REPO", "release": { "factorySha": "40hex", "harnessSha": "40hex", "workflowHash": "64hex", "deploymentName": "factory-runtime", "buildId": "BUILD", "taskQueue": "factory-runtime", "schemaVersion": 1 }, "retainedReleases": [], "requireHumanGate": true }] }`. ## Repository ready-label execution mode (follow-up after the RC)

The regular repository registry may select `approvalMode: "ready-label"` with `requireHumanGate: false`. In this mode `harness:managed` selects Factory tasks and a native `harness:ready` label event from a currently write-authorized human grants execution. The broker freezes that event ID, actor and timestamp together with the existing task/spec/base/policy bindings. Comments or the actor named in a reconcile call do not grant execution. A changed grant, lost permission, closed/unmanaged task or withdrawn ready label blocks admission/authorization. The trusted Manager's native ready→running status transition consumes the exact existing grant without requesting a second confirmation; later changes to the task, blocked status, cancellation or loss of the expected running state still stop authorization. Existing manual-gate installations remain unchanged by default.

In this mode the Manager never applies `harness:ready` itself. A runnable task without a grant rests in `harness:backlog` (also after a revision, a cleared block or a closed review PR); a person adds `harness:ready` and the task starts on the next reconciliation. A grant that is present always wins over the resting status. The Manager asks the runtime for the grant before it writes a delegation intent; without one it creates no intent and reports `runtime admission rejected (READY_…)` with the required step. A policy rejection that the runtime raises after the intent but before persisting or starting a run closes that intent with a `cancelled` result naming the fixed code. Neither case becomes `dispatch outcome uncertain`; that state remains reserved for outcomes that are actually unknown. An intent the runtime has no record of (for example after a transport failure or a crash between the intent and the start) is presented again on every later Manager run with its original execution ID. Admission is idempotent per execution ID, so this either starts the one run or closes the intent with the runtime's definite reason; it never creates a competing intent. This includes closed tasks: the runtime never admits them, so their intent is closed and stops occupying a worker slot. Dry-run and advisory installations are not recovered. While the runtime cannot answer, the intent stays unresolved and is reported. Regression: `tests/runtime-ready-resume.test.ts` replays the Backofficer Issue13 resume of 2026-11-10, where the missing check left an intent without a receipt and blocked the task after the grace period.

A Temporal run whose task is closed or revised while it is running is cancelled on the next reconciliation: its result could no longer be published, and a closed task waiting at a human gate would otherwise hold its worker slot without a time limit.

Where a repository enables `merge`, the broker reviews and merges the pull requests it published for validated runs after each reconciliation (in the background, at most every three minutes). The commit-bound review calls OpenAI with the broker's own `OPENAI_API_KEY`. In production it comes from the GitHub secret `BROKER_OPENAI_API_KEY` of `munichdeveloper/software-factory` (repository or `production` environment): the Factory deploy passes it as `OPENAI_API_KEY` through the action's `deploy-env` input into the release's `.sf-deploy.env`, which the broker reads after the host's `broker.env` (see `docs/deploy.md`). Nothing has to be edited on the host; setting or rotating the secret takes effect with the next deployment (merge to `main` or a manual `workflow_dispatch` of Software Factory Deploy). The broker reaches OpenAI and GitHub through its `front` network; only `private` (the databases) is internal. Without the key the pull request states that no review key is configured and nothing is merged. The repository's own `OPENAI_API_KEY` secret stays with the pinned coding job. Check states come from check runs or, where the installation token cannot read them, from the Actions jobs of the exact head. What the last merge pass could not do is reported with the next reconciliation.

The broker reads the planner choice and the trusted actors from the repository configuration at each use; a configuration change such as a Manager migration applies without restarting it. Every reconciliation that executed, blocked or failed something writes one `factory-reconcile` line with issue numbers and fixed codes to the broker log.

Each managed issue carries one readable status comment (marker `<!-- software-factory:status -->`), edited in place: the lifecycle status, what the Factory is doing, what it needs from a person and the pull request of the latest result. For a blocked task it states the cause and the concrete step: which independent validation checks failed (name, exit code, link to the validation run) from the broker's own bound report, or that the worker itself stopped, together with the worker's own explanation as an inert, clearly marked plain-text quotation. Lifecycle facts, fixed codes and links come from the Factory's records only; the comment is not part of the journal and is never read back as state. A failed write is reported and does not affect the lifecycle.

Registry setup is per repository. `issueNumbers` and `allowedPaths` are optional extra isolation boundaries used for bounded tests in a production-connected repository, not mandatory per-ticket routing configuration. A regular Manager reconciliation still needs to be triggered by an installed caller; adding a label alone does not install a scheduler/webhook or migrate the existing production Manager.
