# v0.7.0-rc.1 — Temporal canary candidate

Experimental opt-in release for a bounded canary. It is not a production-readiness declaration. Existing legacy installations keep their existing runtime/installation contract and are not automatically migrated.

## Included

- Temporal broker, durable PostgreSQL admissions/effects/approvals/artifacts, immutable worker packages and PINNED routing.
- Authenticated human gates, crash/restart recovery, correlation and reconciliation before repeating external effects.
- Isolated Codex compute through pinned Harness `f70d11556075e9764d69ac03e029720d12ccef65`, followed by trusted-broker Draft-PR publication.
- Optional frozen `baseRef` and `executorWorkflow`, separate registry `configPath`, and explicit `issueNumbers` capability scope for testing an existing repository without changing its default branch.

`temporal-runtime.json` describes the opt-in runtime. `installation-contract.json` continues to describe the legacy installation variants; no one-click Temporal UI installer is claimed.

## Fresh package

Build `operations/temporal-runtime/Dockerfile` from the exact reviewed Git commit, passing `--build-arg FACTORY_SHA=<40-character-commit>`. The image compiles the Factory and fetches/builds the exact pinned public Harness source; no credentials or target source enter the build. It runs as the unprivileged `node` account.

Use `pack` to create a worker package, with `--factory-sha`, `--harness-sha`, `--deployment`, `--build`, `--queue` and `--harness /app/.runtime/harness/dist/cli.js`. Mount the generated package at the same absolute path in the worker. Start `serve --file /run/factory/registry.json` with broker-only credentials, then `worker --file /run/factory/worker-package.json` with only the worker role token and Temporal/broker addresses. Never pass the broker environment to the worker. Roles and secret boundary checks reject known broker/model/GitHub credentials in worker environments.

Registry canary fields: `baseRef` is the integration branch, `configPath` is its separate configuration file, `executorWorkflow` is an existing workflow filename whose canary-branch contents are exactly the pinned compute wrapper, and `issueNumbers` contains only the approved test issue. The branch and workflow are frozen into the run snapshot. Moving the selected base or changing its configuration invalidates authorization. Draft PRs target the selected branch, not the repository default branch.

## Backofficer canary

Use branch `test/temporal-v0.7.0-rc.1`, separate configuration `.github/software-factory.temporal-rc.yml`, and the existing filename `factory-manager.yml` for manual-only compute on that branch. GitHub permits dispatching an existing workflow against a selected ref; its default-branch workflow remains unchanged. Keep merge, deployment, notifications and scope expansion disabled in the canary configuration. A single explicitly scoped issue may create a Draft PR targeting only the integration branch. Do not merge that test PR or the integration branch into main.

Check exact RC package/version/Harness hashes, one compute run and Draft PR per execution, restart recovery, positive/negative generated checks, expected denial outside the approved issue, and unchanged Backofficer default-branch SHA and production deployment configuration. Do not overwrite or remove existing repository secrets. A live result must be recorded before marking this canary passed.
